# Sensors through the SLPI — September 24, 2026

The OnePlus 7 Pro's motion, magnetic and light sensors hang off the sensor
DSP (SLPI), not the application processor, so they come through Qualcomm's
sensor stack: the SLPI firmware, FastRPC and a Hexagon file service feeding
it configuration, registry and calibration, QRTR, and SEE (the sensor
framework's QMI protocol), read by libssc and iio-sensor-proxy. The OnePlus
7T Pro port (Robin Snyders, hotdog-linux-bringup) made this work on the same
SoC; this follows its diagnosis, and uses its files only where named (the
hexagonrpcd patches, and the wire format of its SEE client).

## What the 7T Pro needed

- The OEM memory map, with SLPI's 20 MiB at 0x98100000 (`0015`, `0031`,
  `0032`), SLPI enabled with its firmware (`0125`).
- A 16 MiB reusable FastRPC pool below 4 GB, taken by the SLPI FastRPC node
  and assigned to VMIDs 3, 5 and 6 (HLOS, SSC_Q6, ADSP_Q6) (`0126`). Without
  the assignment the hypervisor refuses the DSP's accesses, and a refused
  access stalls the interconnect until the watchdog resets the SoC.
- The sensors protection domain's FastRPC messages from that pool (`0148`):
  through its context bank it addressed memory that was not there.
- A patched `hexagonrpcd` serving a tree with the vendor sensor JSON,
  `sns_reg.conf` (plus lines pointing at the OnePlus project and PCB ids),
  a writable registry seeded from `persist`, socinfo and project ids; factory
  calibration imported read-only from `persist`.
- libssc and an SSC-capable iio-sensor-proxy, started only once the
  accelerometer is published, and a measured accelerometer mount matrix.
- The firmware version mattered most: with its own 00121 SLPI image only the
  SAR sensor registered; OxygenOS 10's 00083 brought up eight sensors.
- SLPI cannot be restarted: every attempt costs a reboot.

## This phone

The stock tree (18821 `sm8150-mtp.dtsi`, `oplus_sensor`) lists an LSM6DSM
accelerometer and gyroscope with a different mounting from the 7T Pro's
(direction 0 against 4), an MMC5603 magnetometer, no light or proximity node
and no barometer. Our SLPI firmware (this phone's OxygenOS 12 H.41 package,
`SLPI.HY.2.2-00121-SM8150AZL-1`, the same version string as the 7T Pro's but
different files) carries drivers for the LSM6DSM, MMC5603 and AK0991x, a
Sensortek STK2232 (light and proximity: I²C 3, address 0x57, IRQ 117, per
`msmnile_stk2232_0.json`) and SX932x SAR parts. The vendor sensor JSON set
matches the 7T Pro's source pool. `dsp.img` holds the 17 SLPI skeleton
libraries.

## Milestone 0: kernel and modules

- **Kernel #193** (`scripts/build_kernel193.sh`): #192 with the boot DTB's
  carve-outs moved to the OEM map (`18821/sm8150-oem.dtsi`). The modem, ADSP
  and IPA regions already matched; video (0x97c00000), SLPI (0x98100000,
  20 MiB), the GPU zap shader (0x99515000, from 0x98b15000, the one moved
  region in use), SPSS (0x99600000) and CDSP (0x99700000, 20 MiB) move; the
  staged fillers over the old locations go; 0x99517000-0x99600000 stays
  reserved. The 16 MiB FastRPC pool is added with its `fastrpc_mem` symbol.
  A check refuses the build if any two reservations overlap. Same code,
  config, command line and release string as #192.
- **`guacamole_slpi.ko`**: overlay setting SLPI's firmware (this phone's
  split `slpi.mdt`), enabling it and giving its FastRPC node the pool and
  VMIDs 3, 5, 6. It refuses unless SLPI's region is the OEM one and the pool
  exists, so it cannot load SLPI over the modem on an older kernel.
- **`fastrpc.ko`** with `fastrpc-sensors-pool.patch` (`0148` without its
  per-call trace, which filled 98% of the 7T Pro's log).
- **`qcom_pd_mapper.ko`** with `pd-mapper-sm8150-slpi.patch`: SM8150's table
  gains SLPI's root and sensor domains (SM8250's entries). It replaces the
  radio set's copy, which loads at boot.

`scripts/build_sensor_modules.sh` builds the three modules.

This phone's SLPI image is relocatable (every loadable segment carries the
relocatable flag) and linked at 0x97300000-0x98700000, exactly 20 MiB, so it
fits the OEM region; the GPU zap shader is relocatable too, and 8 KiB.

Installed on the phone: the SLPI firmware (`slpi.mdt`, `slpi.b00`-`b20`,
`slpir.jsn`, `slpius.jsn`) next to the modem's, the two sensor modules in
`/root/sensors-bringup/modules/<release>/`, and the new pd-mapper in the
radio set (its checksum list updated; the old module and list are kept in
`/root/radio-bringup/modules-backup/<release>-pre-slpi/`). The radio start
loads it at boot; it only adds table entries, so it should also run on #192.
`scripts/flash_kernel193.sh` flashes #193 (`rollback` restores #192), and
`scripts/phone-sensors-test.sh` checks the boot (`check`) and starts SLPI
(`start`).

## Milestone 1: SLPI runs

Kernel #193 booted in the usual time with everything as on #192: modem and
ADSP running, Wi-Fi connected, the sound card present, the flash, torch and
haptics loaded, and the GPU scaling (105 frequency transitions by the time the
desktop was up, so its zap shader loaded from the moved region). The pool is a
16 MiB CMA area at 0xfee00000.

`phone-sensors-test.sh start` loaded `fastrpc.ko` and `guacamole_slpi.ko`.
SLPI booted from 0x98100000 in 140 ms (`remote processor slpi is now up`),
its crash recovery disabled as soon as its remoteproc appeared; the FastRPC
node took the pool (`assigned reserved memory node fastrpc-shared-pool`) and
`/dev/fastrpc-sdsp` appeared (`fastrpc.ko` also binds the ADSP's channel,
`/dev/fastrpc-adsp`, without a pool, as expected). On QRTR, SLPI is node 9
with nine services:

| Service | Instance | Name |
| --- | --- | --- |
| 400 | 0 | Snapdragon Sensor Core (SEE client) |
| 43 | 22 | Subsystem control |
| 66 | 90 | Service registry notification (the sensor domain) |
| 24 | 83 | Thermal mitigation device |
| 51 | 8, 12 | CoreSight remote tracing |
| 15 | 48, 49 | Test |
| 4100 | 0 | Unknown |

One 20 s s2idle cycle (`phone-suspend-test.py`) spent 20.8 s suspended with
no failed device; afterwards SLPI was still running with the same nine
services, and Wi-Fi reconnected.

SLPI stays up until the next reboot; nothing starts it at boot yet.

## Milestone 2: the file service and a census

**hexagonrpcd** 0.4.0 (linux-msm/hexagonrpc, tarball checked against the 7T Pro
port's SHA-512) with that port's four patches
(`devices/oneplus7pro/sensors/hexagonrpcd/`, from hotdog-linux-bringup's
aport, GPL; hexagonrpc is GPL-3.0): writable files, `fremove`, a 64 KiB
listener buffer and the extended `frename`. The DSP writes its registry and
renames temporary files into place, and stock hexagonrpcd refuses both. It is
built on the phone with `HEXAGONRPC_VERBOSE`, so its log records every file
the DSP opens, into `/root/sensors-bringup/{bin,lib}`.

**The served tree** (`phone-sensors-test.sh tree`, into
`/root/sensors-bringup/served`), all from this phone:

| DSP path | Served from |
| --- | --- |
| `/vendor/etc/sensors/config/` | vendor.img, the 65 JSON unmodified (`scripts/build_sensor_vendor.sh`) |
| `/vendor/etc/sensors/sns_reg_config` | vendor.img, unmodified |

The phone last ran LineageOS 23.2 (the September 7 nightly) on the OxygenOS
12 H.41 firmware, and `vendor.img` comes from that LineageOS package, which
carries OnePlus's sensor configuration; `dsp.img` is identical in both
packages. The persist registry was written under that system.
| `/mnt/vendor/persist/sensors/registry/` | a copy of persist's `/sensors/registry` (290 entries, `sns_reg_version`, `sns_reg_ctrl`, `file1`, `file2`), read with `debugfs`, which does not write; persist is never mounted |
| `/sys/devices/soc0/` | generated as Android shows it: `MTP` (SMEM platform 8), subtype `Unknown` (0), soc_id 339, revision 2.2, platform version 65536; every msmnile config gates on MTP and 339 |
| `/usr/lib/qcom/adsp/` | dsp.img `/sdsp`, the 17 libraries |

This phone's `sns_reg_config` names no project file, unlike the 7T Pro's.
Nothing Linux drives sits on the sensor interrupt pins (TLMM 87, 96, 117,
120, 132): all are unclaimed, unlike the 7T Pro's SAR pin.

**Before the attach**, the Sensor Core already answered: only the SUID lookup
sensor, no registry. `scripts/phone-ssc-census.py` is our SEE client
(standard-library Python; the QMI and protobuf layout follow the 7T Pro
port's `ssc-client.py`): it finds service 400 through the QRTR name service
and asks the lookup sensor for each of 63 data types. `--stream SUID SECONDS
[RATE]` subscribes to one sensor and decodes its events.

**The attach** (`phone-sensors-test.sh serve`, once per boot) went through
cleanly: no fault, SLPI still running. In its first 20 s the DSP made about
3,000 file calls (572 opens, 255 writes, 211 renames) and rewrote its
registry from the JSON, as stock does. Its only failed open was
`/proc/oppoVersion/modemType` (9 tries): the firmware's registry code also
knows `prjName` and `pcbVersion` there. On the previous system these came
from the kernel's `oplus_project` driver, which reads OPPO's project record
from shared memory (item 135); OnePlus's own record (item 136) is absent on
this phone. `guacamole_smem_info.ko` (read-only copies in debugfs) shows item
135 as CDT version 1, project 18821, PCB 21 (T5), RF 2, and for a version 1
record that driver deletes `modemType`. The file was missing under LineageOS
too, so it is not what differs.

**Census**: 12 of 63 types.

| Registered | SUID | Streams |
| --- | --- | --- |
| suid, registry, timer, interrupt, async_com_port, resampler, diag_sensor, sensor_logger, data_acquisition_engine | framework | |
| proximity | `4895ecea…1477` | far, raw 42 (event 769) |
| wise_light (OnePlus ambient light) | `4895ecea…1071` | about 5 Hz; first value about 99 in a lit room (event 1025) |
| sars | `73356639…70ca` | yes (event 769) |

Missing: accel, gyro, mag and sensor_temperature (the LSM6DSM and MMC5603),
and with them every derived type (gravity, rotation vectors, motion and
orientation detectors, pedometer and OnePlus's own), which all wait on the
accelerometer. This is the 7T Pro's 00121 result, but one step further:
the light and proximity sensor registers here. The pattern is the bus: all
three that register are on the sensor DSP's I²C bus 3; the LSM6DSM is on its
SPI bus 2 and the MMC5603 on I²C bus 1. All use the same two rails. On the
7T Pro, the older OxygenOS 10 firmware (00083) registered all eight, with
all config changes reverted, and the reason 00121's LSM6DSM never registers
was not found.

## Milestone 3: OxygenOS 10's SLPI firmware

Two leads turned out not to be the difference. `modemType` is missing under
the previous system too (above). And nothing in the previous kernel touches
the sensor buses: its SLPI loader and `msm-ssc-sensors` driver only load
SLPI and offer a timer, and its SLPI pin controller node is disabled (SLPI
sets up its own pins). So, as on the 7T Pro, the older firmware.

**Source.** OnePlus's own server no longer answers; the Wayback Machine keeps
the full OxygenOS 10 Global package for the 7 Pro,
`OnePlus7ProOxygen_21.P.31_OTA_031_all_2011052258_42a665d7dc95490e.zip`
(build `OnePlus7ProOxygen_21.P.31_GLO_031_2011052258`, Android 10, November
2020; 2,270,417,933 bytes, SHA-256 `6eb1422f…5560b8`), kept whole in the
ignored `.work/firmware/oos10-p31/` in case the project needs more from it.
`scripts/fetch_ota_partitions.py` extracts partitions from an A/B package,
local or over HTTP ranges, checking every operation's and partition's hash.
Its `modem` image carries `SLPI.HY.2.2-00083-SM8150AZL-1`, the version that
worked on the 7T Pro: 22 segments, every size matching its program header
and every hash present in the signed hash table, relocatable, the same
20 MiB span. Its LSM6DSM driver is a different build from 00121's; it has
the TCS3701 driver 00121 lacks.

**Firmware sets.** `/root/sensors-bringup/firmware/{00121,00083}/` (with
checksums); `phone-sensors-test.sh firmware SET` installs one as the SLPI
image, only before SLPI starts. Only the firmware changed: the same 65
configuration files, a fresh copy of the persist registry and the same
libraries, the combination that worked on the 7T Pro. OxygenOS 10's own 61
configuration files (different driver names, `mmc5603x` against
`mmc5603nj`) are kept as a fallback.

**Result.** TrustZone accepts the older image; SLPI booted in 108 ms, and
the attach went through as before (about 2,950 file calls, the registry
rewritten, the same `modemType` miss). The census found **42 of 63 types**:

- physical: accel, gyro, mag, ambient_light, proximity, sensor_temperature,
  sars;
- derived: gravity, rotv, game_rv, geomag_rv, gyro_cal, mag_cal,
  motion_detect, amd, rmd, device_orient, tilt, sig_motion, pedometer,
  basic_gestures, facing, multishake, bring_to_ear, ccd_walk, ccd_ttw, cmc,
  fmv, psmd, dpc, distance_bound, tilt_to_wake, aont, oem1;
- the framework sensors, as before.

The accel, gyro and mag SUIDs match the 7T Pro's under 00083. OnePlus's own
types from 00121 (wise_light and the rest) are gone; the light sensor
appears as the standard `ambient_light` instead.

| Sensor | Streamed (phone flat on a desk) |
| --- | --- |
| accel | 25 Hz; (−0.12, −0.17, 9.91) m/s² |
| gyro | about 25 Hz; first sample 1.1 rad/s flagged unreliable, then about (0, 0, −0.02) rad/s |
| mag | (−33.2, 48.6, 1.8) µT, 59 µT in all, a plausible Earth field |
| ambient_light | about 5 Hz; about 107 |
| proximity | far |

The census is in `out/sensors/census-00083.txt`.

**Physical checks** (`scripts/phone-sensor-physical-check.py`, which buzzes
the phone at each step; subscriptions start 1.5 s apart, since two clients
subscribing at the same moment lost one stream):

| Position | Accelerometer (m/s²) |
| --- | --- |
| portrait, top edge up | (−0.29, **+9.71**, 0.14) |
| landscape, left edge down | (**+9.61**, 2.12, −0.40) |
| flat, face up | (−0.14, −0.23, **+9.90**) |
| flat, face down | (0.00, −0.23, **−9.82**) |

+x is the right edge, +y the top edge, +z out of the screen: Android's device
frame, so SLPI already applies this board's mounting (from the registry).
The matrix iio-sensor-proxy needs follows from its own convention, to be
checked once it runs.

The light sensor responds: about 111 face up in the room, 15 face down (not
0: the sensor sits under the display, which lights it). Light only streams
with a sample rate (`--stream SUID SECONDS RATE`); proximity only on change.

The STK2232's proximity channel does not: it stayed far with a raw reading
of 0 to 2 (threshold 84) with a hand over the top of the screen and face
down on a desk. The previous system's sensor HAL (`sensors.ssc.so`) lists an
"Elliptic Promixity" sensor, the vendor image references `/dev/elliptic1`,
and the 7T Pro's proximity is Elliptic Labs ultrasound on the audio DSP. On
this phone too, proximity is most likely ultrasound, a separate piece of work
through the ADSP; the STK2232's proximity half appears unused.

## Boot

`devices/oneplus7pro/sensors/start.sh`, installed as
`/usr/local/sbin/guacamole-sensors-start` and enabled by
`/root/sensors-bringup/autostart-enabled`, runs from the session hook
(`desktop-prepare.sh`) once per boot, on kernel #193 or later. It waits for
the radio start (which loads pd-mapper, and so the DSPs boot one at a time),
checks that the installed SLPI image is the active firmware set
(`firmware/active`, now 00083), then runs `phone-sensors-test.sh`'s `start`,
`tree` and `serve` steps (installed as `/root/sensors-bringup/bin/sensors-test`)
and marks `/run/guacamole-sensors.ready`; it keeps the last ten hexagonrpcd
logs. The registry is copied fresh from persist every boot, so what the DSP
learns (its own calibration updates) lasts until the next reboot.

On the first boot with it, SLPI was up at 159 s and the sensors ready about
20 s later; the census found accel, gyro, mag, ambient_light,
sensor_temperature, rotv and device_orient, with the modem, ADSP, Wi-Fi,
controls and shell as before.

## Milestone 4: Linux's sensor service and the shell

**iio-sensor-proxy.** Arch Linux ARM's own packages do it: iio-sensor-proxy
3.9 is built against libssc 0.4.4 (Dylan Van Assche's SEE library, which
speaks QMI to service 400 over QRTR), so nothing is patched or built here.
Its udev rule gives the FastRPC nodes only light and the compass;
`devices/oneplus7pro/sensors/81-guacamole-sensors.rules` (installed in
`/etc/udev/rules.d/`) adds the accelerometer on `fastrpc-sdsp` and its mount
matrix. Proximity is left out (the light chip's half never reads near). The
boot script starts the daemon once the accelerometer publishes (there is no
system manager to activate it), and it serves `net.hadess.SensorProxy` on
the system bus: the accelerometer, and the light sensor (`stk_stk2232`) in
lux.

**Mount matrix.** iio-sensor-proxy's orientation code (inherited from
sensorfw) calls positive x "left-up" and positive y "bottom-up": the reverse
of Android's frame, which SEE reports (+y is the top edge, measured above).
Without a matrix, left edge down read "left-up". The rule sets
`ACCEL_MOUNT_MATRIX` to `-1, 0, 0; 0, -1, 0; 0, 0, 1`, the half turn the
7T Pro used; tilt (z) is unchanged.

**The claim race.** Version 3.9 takes its D-Bus name before it opens its
sensors, and a claim in that window is counted but never starts the sensor:
later claims only add to the count, so the sensor stays silent. Restarting
the daemon under running clients reproduced it (`monitor-sensor` re-claims
the moment the name reappears, about 30 ms before the sensors open). The 7T
Pro port fixed the daemon (its patch 0010, which does not apply to 3.9);
here the only clients are the shell's helpers, so they wait instead: they
start `monitor-sensor` only once `HasAccelerometer` or `HasAmbientLight`
reads true, which 3.9 sets after opening the sensor, and start over when the
daemon vanishes. A daemon restart under running clients then resumed data by
itself (claims 3 s after the sensors opened), and so did a full boot.

**Automatic brightness** (`omarchy-mobile-controls auto on|off`, the sun
icon beside the shade's slider). A resident follower (`auto-run`) reads lux
from `monitor-sensor --light` and sets the slider's (perceptual) level on a
log curve, `10 + 17 * log10(lux + 1)`, shifted by the user's preference: the
slider's final level in the current light is learnt as that offset. The
light sensor sits under the panel, which adds to its reading: in a room of
about 110 lux it read 113 at 5%, 128 at 30%, 176 at 60% and 301 at 100%,
about 190 lux times the panel's output share, which the follower subtracts
before the curve (without it, brightness would chase its own light). The
filter brightens quickly and darkens slowly, and a change is made only when
it is at least 4 slider points and 2 s after the last: each change is a
panel command, and a command can flicker (the backlight still goes outside
the display commit). The user saw no flicker, and the level changes in
steps; smooth ramps wait for the backlight to go through the commit. A slider
drag is left alone for 5 s. Tested by `tests/test_controls.py`.

**Rotation**, as the user chose: Android's rotate button rather than
automatic rotation. `overlay/mobile/rotation.py` (`omarchy-mobile-rotation`)
follows `monitor-sensor --accel` while the screen is on, releasing the
accelerometer when DPMS turns it off, and `RotateButton.qml` shows a round
button in the bottom-right corner for 5 s whenever the phone is held
differently from the screen; tapping it sets the output's transform
(`hl.monitor` with the device profile's mode and scale, so 90 Hz is kept:
Hyprland's `preferred` mode is 60 Hz) and the touchscreen's with it (touch
does not follow the output by itself: the first try left touch dead).
Left-up is transform 1, right-up 3, bottom-up 2, checked by hand in both
landscape directions. The shell's own surfaces (status bar, shade, app
drawer, keyboard) lay out in landscape unchanged (screenshots in
`out/rotation/`). Both helpers' `monitor-sensor` children die with them
(`PR_SET_PDEATHSIG`): a shell restart kills its helpers outright, which
first left an orphan holding a light claim.
