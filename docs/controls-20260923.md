# Controls: brightness, vibration, flashlight and alert slider — September 23, 2026

The "quick wins" from the [hardware plan](hardware-plan-20260922.md): four
controls a phone is expected to have, each brought up at runtime on kernel #191
(overlays and modules, no reflash) and user-confirmed on the handset.

| Control | Result |
| --- | --- |
| Brightness | Works; the shade has a slider and the level survives restarts. Dragging can flicker the screen (below). |
| Vibration | AW8697 identified and driven through the standard force-feedback interface; both test buzzes felt. |
| Flashlight | Both rear LEDs light, with no fault flags; a shade toggle drives them. |
| Alert slider | Vibrate and Ring work. The Silent contact never closes on this unit: a hardware fault. |

## Sources

The OnePlus 7 Pro's own stock tree is in the LineageOS kernel source
(`arch/arm64/boot/dts/18821`); the OnePlus 7T Pro port (Robin Snyders,
hotdog-linux-bringup, GPL-2.0) has working mainline versions of all four.

- **Slider**: `sm8150-oem.dtsi`, `oplus, tri-state-key`: TLMM GPIOs 27, 134
  and 125, active low, 2 mA, no internal bias (the board pulls them up). The
  stock truth table has one contact low at a time: 125 Silent, 134 Vibrate,
  27 Ring. The 7T Pro uses the same GPIOs.
- **Haptics**: the same file puts an Awinic AW8697 at 0x5a on QUP SE7 (mainline
  `i2c7`, `i2c@89c000`), reset on GPIO 116, interrupt on GPIO 24, device id
  619. The stock driver picks its 170 Hz "0815" actuator profile (drive level
  60, overdrive 125) for every id but 832 and 833, so this phone uses the same
  profile as the 7T Pro, whose driver (`0130`) is reused unchanged apart from
  a note to that effect. The PM8150B haptics block is not what stock drives.
- **Flash**: `pm8150l.dtsi` and `sm8150-oem-camera-t0.dtsi`: flash channels 0
  and 1 together, 1 A per channel for a flash (1.5 A maximum), 300 mA for
  torch (500 mA maximum), 1.28 s at most; channel 2 unused.
- **Brightness**: the panel driver's DCS backlight, 0-1023, 320 at boot.

None of the GPIOs is in the TLMM's reserved ranges (0-3, 126-129).

## Runtime pieces

`scripts/build_controls.sh` builds, against the #188-#191 module tree:

- `guacamole_alert_slider.ko`: a gpio-keys overlay on the sound-profile axis
  (`ABS_SND_PROFILE`, 0x22, values Silent 0, Vibrate 1, Ring 2, written as
  numbers because they reach the kernel after 6.17), with the pins set to no
  bias; the kernel default is a pull-down, which reads low whatever the
  slider does.
- `guacamole_haptics.ko` (enables `i2c7` and describes the AW8697) and
  `aw8697-haptics.ko` (the 7T Pro driver, `FF_RUMBLE`).
- `leds-qcom-flash.ko` (mainline's driver, not shipped on the phone) and
  `guacamole_flash.ko`. The flash block lives at PM8150L's second slave id,
  `pmic@5`, which our tree leaves disabled, and the SPMI bus creates devices
  only when it starts, which is why PM8150L's first slave id needed kernel
  #190. The loader instead applies the overlay (`pmic@5` and the flash block
  enabled, two channels, currents as stock, the first named `white:torch`)
  and then registers the SPMI device for slave id 5 itself, as the SPMI core
  does at boot (`spmi_device_alloc`/`spmi_device_add`, reaching the
  controller through `pmic@4`'s device). The PMIC driver then creates the
  flash device and the driver binds. SPMI device `0-05` appeared and both LEDs
  registered without faults.

`scripts/phone-controls-test.sh slider|haptics|flash` loads one stage at a
time for testing; `devices/oneplus7pro/controls/start.sh`, installed as
`/usr/local/sbin/guacamole-controls-start` and enabled by
`/root/controls-bringup/autostart-enabled`, loads all five at session start
from `session-prepare`, continuing past one that fails; it waits for the SPMI
bus, which the boot power overlay starts some 20 s after the desktop, before
the flash. Nothing unloads; reboot to undo.

## Hardware results

- **Brightness**: 120 and 700 were each written, read back and seen by the
  user, then 320 restored.
- **Vibration**: the probe read chip id 0x97 on `i2c-5` and registered
  "Awinic AW8697 haptics". A 150 ms pulse at 25% and a 250 ms pulse at 50%
  through `EVIOCSFF` were both felt.
- **Flash**: each LED alone and then both, at brightness 32 of 255 for 2 s:
  the user saw all three and called them bright. `flash_fault` stayed empty.
- **Slider**: over two full passes the Vibrate and Ring contacts fired (10 and
  4 edges); the Silent contact (GPIO 125) never changed. It reads high at the
  top, so the board pull-up works and the contact never closes to ground; the
  user found the slider soft. Silent is therefore unavailable from the slider
  on this unit, and the stock-derived mapping stands for a working one.

## Shell integration

`omarchy-mobile-controls` (`overlay/mobile/controls.py`) finds everything
through standard classes, so the shell carries to other phones: the first
backlight, LEDs named `*:torch`, `*:flash` or `*:flash-N`, the first input
device with `FF_RUMBLE`, and devices reporting the sound-profile axis. It
reports status, sets brightness (the slider's share squared, never below 1%
of the range, remembered in `~/.local/state/omarchy-mobile/controls.json`),
restores it when the shell starts, drives every flash LED at half its torch
range (150 mA each here), plays one bounded vibration (10-1000 ms), and
streams slider changes.

- **Shade**: a Torch toggle beside DND and a brightness slider under the
  toggles. The handle does not jump back on release, and a drag is rate
  limited (below).
- **Slider policy**, as on Android: Vibrate and Silent mute the ring group,
  Ring unmutes it, media is untouched, and reaching Vibrate buzzes briefly.
  Only movements count. `omarchy-mobile-volume` gained `mute GROUP on|off`.
  Checked: after a move to Vibrate the ring group read muted.
- **Notifications** buzz for 150 ms at 70% unless Do Not Disturb is on, the
  slider is on Silent or the notification is low urgency. The user felt a test
  notification's buzz.
- **Automatic brightness** (September 24): `auto on|off` and a resident
  `auto-run` follower of the light sensor, switched by the sun icon beside the
  slider; see [sensors](sensors-20260924.md#milestone-4-linuxs-sensor-service-and-the-shell).

## Brightness flicker while dragging

Dragging the slider showed brief flashes with lines. Each burst matched
`dsi_err_worker: status=5` and `status=4` in the kernel log: the DSI host's
command timeout and FIFO flags, as the 7T Pro port recorded on this panel
family at 90 Hz. The panel runs in command mode, so frames cross the link only
when the screen changes. Forty brightness writes on a still screen, 300 and
50 ms apart, produced no errors; a drag redraws the slider every frame, and a
write can land during a frame transfer. The host already sets
`BLOCK_DMA_WITHIN_FRAME`, which is meant to hold commands until the frame
ends.

Stock's display driver (`dsi-staging/dsi_display.c`) waits before sending
commands to a command-mode panel: `dsi_ctrl_hw_cmn_wait_for_cmd_mode_mdp_idle`
polls bit 2 of `DSI_STATUS` (`CMD_MODE_MDP_BUSY`) every 2 ms for up to 200 ms.
Mainline's `msm_dsi_host_xfer_prepare()` has a TODO at exactly that point
("make sure dsi_cmd_mdp is idle"). Kernel #192 added that wait and it did not
help ([kernel #192](kernel192-20260923.md)): the command collides with the
frame that starts next. Stock sends the backlight command inside the display
commit, just before the frame kickoff; the fix is to route the backlight
through the DRM commit.

Until then the shade limits the rate. A first version sent at most five
levels a second, each by starting the helper: it still flickered, and the
screen lagged the slider. Now one resident helper (`omarchy-mobile-controls
serve`) takes the levels on its standard input: the first move of a drag
applies at once, then at most one level every 80 ms, then the last, which is
remembered.
