## Brightness flicker

Dragging the brightness slider flickered the panel, with a burst of
`dsi_err_worker: status=5` (DSI timeout and FIFO errors) in the kernel log
([controls](controls-20260923.md)): a backlight DCS command collided with a
frame transfer. #192 made each command wait for `CMD_MODE_MDP_BUSY` to
clear, which did not help ([kernel #192](kernel192-20260923.md)). In command
mode a kicked-off frame waits for the panel's tear signal before it
transfers, so the controller reads idle, the command starts, and the frame
starts under it. Downstream avoids that by sending the backlight inside the
display commit, before the kickoff.

`devices/oneplus7pro/kernel/display/dsi-cmd-frame-sync.patch` serializes the
two in the msm driver. The command mode encoder publishes its pending frame
count (`pending_kickoff_cnt`, which the pingpong-done interrupt decrements
and wakes) in `msm_drm_private` while it is enabled. A DSI command takes
`cmd_xfer_lock`, waits up to 50 ms for pending frames to drain, and is sent;
a kickoff takes the same lock, so no frame starts while a command is on the
link. The kickoff runs under the commit's CRTC mutexes in process context,
and the DSI path never takes those, so the lock order cannot invert.

| | #193 | #194 |
| --- | --- | --- |
| Slider dragged back and forth for ~5 s | 10 `dsi_err_worker` (status=5), flicker seen | 0, no flicker (user) |

It booted in the usual time with the display, GPU, shell, sensors, modem,
ADSP and Wi-Fi as on #193.

Automatic brightness could then fade instead of jumping: `controls.py`'s
follower moves a slider point every 40 ms, at most a second per change. The
user saw smooth fades and no flicker, and the log stayed at 0 errors.
