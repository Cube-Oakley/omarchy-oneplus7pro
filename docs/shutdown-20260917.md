# Power-off attempt rebooted the phone — 2026-09-17

The user tried `shutdown now` inside Arch and received the chroot refusal.
PID 1 is the BusyBox initramfs shell script, not Arch systemd.

From the outer USB recovery shell, Arch-rooted processes were stopped,
`sync` was run, and `/newroot` was successfully remounted read-only. Then
`busybox poweroff -f` issued a power-off request directly, bypassing the
initramfs shell's lack of a normal init shutdown handler.

Evidence: `out/power-test/shutdown-20260917.log` contains:

```
SHUTDOWN_BEGIN
/dev/sda19 on /newroot type ext4 (ro,relatime,stripe=128)
POWER_OFF_REQUEST
```

USB disappeared and ping stopped responding. The assistant incorrectly called
this successful power-off. The user observed the handset **rebooting** instead.
Treat that observation as the outcome; USB disconnect is insufficient proof.

The current source config already enables `CONFIG_POWER_RESET_MSM`,
`CONFIG_POWER_RESET_QCOM_PON`, and ARM PSCI firmware support. This does not
establish that the appropriate device-tree nodes/drivers are active or that
the PMIC receives a shutdown rather than reset configuration.

Next investigation: inspect the actual booted DT, power-off handlers and PMIC
PON/PS_HOLD path, any firmware interaction and whether USB power causes a
restart after shutdown. Capture shutdown/next-boot evidence where possible.
Distinguish failure to power off from power-off followed by automatic power-on;
the cause has not been determined. Validate that the handset stays off, then
add a usable shutdown command/control outside the current chroot limitation.

No second power-off attempt was made after the user's correction.
