## Preparing a hardware wake alarm

`scripts/build_rtc_test.sh` builds the stock `rtc-pm8xxx` driver for the exact
native4 kernel, plus a temporary single-node overlay. An offline merged-DT
comparison shows only PM8150 RTC status changes from disabled to okay.
No `allow-set-time`, NVMEM offset or UEFI offset is enabled; the vendor counter
and persistent factory clock data are not written by the test.

The first live overlay produced an unbound RTC device at the platform root.
The generic OF change notifier only finds platform parents, while the PMIC is
an SPMI device; the driver could not obtain the parent's regmap. A narrowly
scoped helper recreates only this unbound RTC child under its actual SPMI
parent. This is specific to live overlay testing; enabling the node before
the PMIC initially populates its children does not need that repair.

RTC registration invokes the kernel's HCTOSYS path. The load helper preserves
the NTP-corrected system clock across registration using elapsed monotonic time,
without setting the RTC. The RTC's raw date must not be interpreted as UTC
until its vendor offset has been understood. Alarm validation is done while
awake before attempting a timed suspend. The modules are not boot-persistent.

Reference: [kernel suspend testing](https://docs.kernel.org/power/basic-pm-debugging.html)
and [sleep-state definitions](https://docs.kernel.org/admin-guide/pm/sleep-states.html).

## RTC and first two suspend trials

The repaired RTC device bound successfully, and `rtcwake -m on -s 5 -u` fired
its alarm while awake. Its raw counter was 265003 seconds (January 1970 without
the vendor offset). The load helper restored the correct system time immediately.

`scripts/phone-suspend-test.py` temporarily disables asynchronous PM callbacks,
blanks the display, syncs storage, and invokes an RTC-backed s2idle trial. It
restores the callback setting, clears the alarm, and restores the display on
return. It is diagnostic only; no normal power-button or idle policy changed.

The first 20-second alarm test spent 18.03 seconds suspended. Kernel success
count rose to one, but the touchscreen resume callback returned -ENODEV.
Wi-Fi reassociated, USB returned, the desktop remained alive, and charging
resumed. A later HTTPS check passed; the immediate post-resume DNS check failed
during Wi-Fi reassociation/roaming. The first helper version only asserted time
asleep and syscall success; it has since been tightened to reject any new
device suspend/resume failure counters as well.

The touchscreen resume routine enabled its interrupt before resetting the
controller and polling its boot-complete event. The IRQ handler reads the same
event FIFO. The new `s6sy761-resume-irq.patch` keeps the IRQ disabled through
initialization and restores sensing when the input device remains open.
`build_touch_test.sh` applies it after the existing patches. A separate build
under `.work/suspend-touch-test` preserved the original native4 module; the new
module was hot-loaded via USB without changing the flashed image.

With this patch, the second trial slept 18.02 seconds and returned with no new
failed resume count (the historical count remained one). HTTPS over wlan0
passed afterward. Both trials logged an ath10k key-removal timeout and the
existing USB HS-PHY L2 warning; their underlying causes are unresolved.

A separate userspace issue remains: physical input devices disappear from
Hyprland after the VT/seat suspend cycle, even when kernel resume succeeds.
An input-only `udevadm trigger --action=add` restores touchscreen and power-key
discovery without restarting the compositor. That step is now in the test's
resume cleanup; a combined test is pending. The user confirmed that touchscreen
and app launcher work after the corrected driver and manual input rediscovery.
Do not equate successful driver resume with working UI.

Neither the RTC nor the replacement touchscreen module is reboot-persistent.
The original native4 image remains the recovery baseline.
