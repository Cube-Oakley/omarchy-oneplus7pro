# Kernel #192 — September 23-24, 2026

#191 plus crash handling and a display change, built by
`scripts/build_kernel192.sh` (output `out/checkpoints/20260923-kernel192/`)
and flashed to `boot_b` with `scripts/flash_kernel192.sh`; `… rollback`
restores #191. Same release string, and the configuration differs only by the
lockup detectors, which change no structure a module sees, so every runtime
module loads unchanged (their interrupt-storm check, which adds a per-IRQ
statistics field, is off; the build refuses any other config change).

| Change | Result |
| --- | --- |
| Crash-dump mode cleared at boot | Works: a crash now reboots the phone instead of stopping in `05c6:900e` |
| Soft and buddy hard lockup detectors, panic on lockup, `panic=10` | On (`softlockup_panic=1`, `nmi_watchdog=panic`); not yet met a real lockup |
| ramoops at the stock `0xa9800000` | Registers, but nothing survives the reset |
| DSI command-mode idle wait (brightness flicker) | No effect |
| PM8150L slave id 5 in the boot DTB | No effect: the boot power overlay disables it |

The phone booted #192 in the usual time (desktop and power at about 140 s:
the display and GPU are held back on purpose) with audio, Wi-Fi, Bluetooth,
the modem, the ADSP and the controls as on #191.

## Crash-dump mode

Every crash so far left the phone in Qualcomm's crash-dump mode, which only a
three-button reset leaves: the bootloader arms "download mode", and mainline
clears it at boot only if the SCM node says where the flag lives. Stock keeps
it in TCSR_BOOT_MISC_DETECT, `0x1fd3000` (`restart@c264000`,
`tcsr-boot-misc-detect`), the register newer Snapdragons describe as
`qcom,dload-mode = <&tcsr 0x13000>`. Our tree's TCSR syscon starts at
`0x1f60000`, and the driver adds the offset to the node's address without a
bounds check, so #192 sets `qcom,dload-mode = <&tcsr_regs_1 0x73000>`.
`download_mode` reads `off` and the SCM driver reported no error.

Two deliberate crashes (`echo c > /proc/sysrq-trigger`, with the camera stack
unloaded) proved it: USB dropped 11 s after each crash (the panic delay) and
the phone was back on USB 37 s after it, booted into #192, with no 900e and
no button press.

## ramoops

The 4 MB region is reserved and pstore registers ramoops on it, the step that
hung during early bring-up (docs/status.md), but after both crashes pstore
was empty: not even the console record, which any reboot with preserved RAM
would leave. The second crash was taken with `/sys/kernel/reboot/mode` set to
`warm` (PSCI 1.1, so the kernel can ask for `SYSTEM_RESET2` warm reset), with
the same result. Either the firmware wipes or reuses that memory while
booting, or it resets cold regardless. Next: write a pattern into the region,
reboot, read it back, and compare stock's reset path (warm reset through the
PMIC's PON configuration).

## Brightness flicker

The idle wait (`dsi-cmd-mode-idle-wait.patch`: poll
`DSI_STATUS0.CMD_MODE_MDP_BUSY` before each command transfer, as the
downstream driver does) did not help: a drag still produced nine
`dsi_err_worker: status=5` reports, and the MDP never read busy when a command
started. The command collides with the frame that starts next rather than one
in progress. Stock avoids that by sending the backlight command inside the
display commit, just before the frame kickoff, so commands and frames are
serialized by design; the fix here is to route the panel's backlight update
through the DRM commit rather than a free-standing DSI write. The wait is
harmless and stays for now.

## PM8150L slave id 5

`pmic@5` is enabled in #192's boot DTB, but the SPMI bus starts only when the
initramfs power overlay (`power_support.ko`, frozen with kernel #190) is
applied, and that overlay sets `pmic@5` to disabled. The flash therefore still
relies on its loader registering slave id 5 at runtime; the loader now works
either way. At boot the controls start script also has to wait for the bus
(about 20 s after the desktop) before loading the flash, which it now does.
