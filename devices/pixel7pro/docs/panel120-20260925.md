# Pixel 7 Pro: 120 Hz panel and desktop investigation — 2026-09-25

The user confirms v17's direct scanout looks correct and smooth, but the mobile
interface still feels laggy. The target is native, accelerated 120 Hz, not a
cosmetic refresh-rate setting. All work here uses temporary RAM boots, without
flashing partitions, changing slots, or editing the OnePlus project.

## Separate the bottlenecks

The v17 desktop really uses the Mali-G710 MC7. Hyprland's renderer log and both
Hyprland/Quickshell library maps identify the isolated Panfrost Mesa 26.2.3 build.
Quickshell uses the OpenGL RHI. No software-rendering override is present. This
rules out software rendering as the explanation for all remaining latency; it
does not establish correct frame pacing or fast input. CPU policies remain
bounded and the GPU runs at its lowest validated 302/202 MHz clock pair. Touch
still uses temporary GPIO SPI polling. The original Lua feasibility config has
a stale software-rendering comment; the launcher's actual hardware gate and
runtime renderer are the relevant evidence.

Evidence: `out/checkpoints/20260925-panel120/{ui-baseline,ui-libraries}.txt`.

## Establish actual panel communication and timing

The retained DSIM0 accepts standard DCS reads without touching its PLL, PHY,
reset or power. Panel ID is `0a 80 06`, power readback `9f`, display control `20`
(non-HBM), pixel format `77`. F0 key unlock/read/relock identifies the expected
HS/manual baseline: B9 is initially `00 04 00 00 0c 42 00 1b 0c 42 00 1b 0c 42
00 1b`; BD starts `21 81 83 03 03`. A one-byte B9 read misleadingly returns zero:
the useful state requires the longer response. DCS60 reads zero even after a
verified 60 Hz restore, so it is not used as proof of refresh rate.

DSIM version is `02060000`, configuration `04887cff`. The actual PLL registers
are `1202/1355/db`, matching the pinned 1346 MHz mode. Boot timer/underrun/TE0 are
`33eb3b26/1f09/56`. These become strict guards for the integrated mode controller.
B9's first byte changes from zero to `04` after the 60 Hz restore, while the
remaining TE-width bytes and BD baseline are restored. The initial-boot guard
intentionally checks the untouched firmware state, not an arbitrary used panel.

The DECON extra interrupt's TE_RISE observer sees only sparse events while
DECON is idle. It must not be called a continuous optical refresh measurement.
During animation it measures 600 intervals near 16.67 ms and six near 33.33 ms,
consistent with the approximately 59 fps v17 desktop. Its interrupt masks are
restored on stop/unload. The probe uses the extra IRQ only; it does not claim
v17's frame-start or frame-done IRQs.

Source probes: `mainline/pixel-{dsi-read,te,refresh}-probe.c`. The read-probe
variants and build inputs are preserved under the checkpoint directory.

## Reversible 120 Hz experiment

Primary source is Google's pinned [S6E3HC4 panel driver](https://android.googlesource.com/kernel/google-modules/display/+/0137241105270acf53c329e899ea9c4b6b1c8e66/samsung/panel/panel-samsung-s6e3hc4.c),
plus `samsung/exynos_drm_dsim.c` and `samsung/cal_9845/dsim_reg.c` at that same
revision. The local source hashes are in the v16 research manifest.

Both WQHD modes use 1440×3120 pixels, totals 1580×3150 and the same DSC geometry.
The mode transition sends the entire correlated HS/non-HBM/manual group in one
packet-go batch: F0 unlock, fixed/changeable TE, early-exit group, indexed BD
step settings, manual frame mode, frequency, F7 update, F0 lock. It changes no
voltage, brightness, PLL, PHY or compression settings. The probe requires the
compositor stopped and DECON idle, and restores 60 Hz on unload or after 60 s.
It is a development experiment, not a concurrent production display owner.

Measured results with four immutable native DMA buffers:

| Test | Result |
| --- | --- |
| Panel commands only | 1,441 flips / 12.007 s = 120.009 fps |
| Panel plus vendor host timing | 1,441 flips / 12.007 s = 120.010 fps |
| Return to 60 Hz | 300 flips / 5.001 s = 59.987 fps |

With vendor host timing, all 1,442 observed TE intervals are 8.304–8.364 ms.
There are 2,886 matched starts/completions after both 120 Hz runs, zero scanout
failures, zero CPU pixel copies, and seven temperatures between 41 and 47°C.
The later 60 Hz control reaches 3,188 matched transfers with zero failures.

The panel-only test also proves the original host settings did not themselves
prevent 120 Hz; the host update brings the timing into agreement with the vendor
120 Hz mode. At 1346 MHz, 4 lanes, DSC 3:1, `te_var=1`, `te_idle_us=350`, the
vendor underrun formula yields 1004 LP units; TE0 is 28 and timer is `1a031e1f`.
All three registers restore their exact saved values at 60 Hz.

Evidence: `panel-only-test.txt`, `panel-host-test.txt`, `restore-60-check.txt`.
The first test's final debugfs read failed because debugfs was not yet mounted;
the flip and TE results succeeded, and the exit trap restored 60 Hz. Debugfs
was mounted for the second test. An initial animation observer attempt used the
wrong module path and loaded nothing; `te-animated-retry.txt` is the actual run.
One probe compile had an extra diagnostic printf argument; it was corrected
before the host-timing test. The corrected probe passes checkpatch and builds
without that warning.

## Frame-start presentation, image C

Google's `decon_check_fs_pending_locked()` sends its pending vblank event at
frame start. V18 image C likewise sends the flip event only after the real
frame-start IRQ and matching active-shadow DMA address. It timestamps/counts
that start rather than the end of the transfer. It still waits for frame-done
and idle before releasing framebuffer references or finishing hardware commit
work. The pending event is owned independently of `crtc->state`, since userspace
can queue its next atomic state after receiving the event. A separate armed
flag prevents a stale start interrupt from consuming a newly queued event.
Failure/missed-start fallback releases only its own saved event and is counted.
This is on-demand frame-start timing, not continuous idle-panel TE accounting.

Image B was built but never booted; C adds the stale-interrupt guard before any
hardware test. C SHA256:
`62e52188634f4dd59a464dfc7b6ca8aac947c205b35ac9068d4202da9f560eec`.
Both files pass checkpatch, the kernel build has no compiler warnings, and its
cumulative patch passes a separate clean-base apply check. Runtime comparison
is pending.

A test-tool tarball initially applied the host user's ownership to `/root`, so
OpenSSH correctly refused subsequent authentication. USB serial remained
available; restoring root ownership and mode 0700 fixed access. The saved bundle
now uses numeric owner/group 0 and mode 0700. No SSH security setting was relaxed.

Image C's early-event path is working: native modes pass at 60.157/120.082 fps,
1,744 start events, zero late-event fallbacks and zero DMA failures. However,
the compositor remains at approximately 60 fps. Holding the CPUs at their
already-bounded maximum frequencies also leaves it at 60 fps; schedutil is
restored afterward. These results do not support CPU scheduling or notification
timing alone as the remaining throughput explanation.

## Physical artifact, underrun diagnosis and memory bandwidth

The user reports full-width flashing horizontal lines across the moving GPU
triangle. Testing stops and the compositor exit restores 60 Hz. The user then
confirms native immutable moving bars at 120 Hz are clean, with no glitches.
The native run completes 14,403 flips in 120.007 seconds (about 120.018 fps).
This physical comparison is essential: DMA completion counters alone do not
establish clean panel output.

A read-only register inventory finds DSIM underrun pending (INTSRC bit 19),
which the older driver did not count. The bounded monitor acknowledges only
that W1C bit, then counts new observed pending episodes at 1 ms polling intervals:

| Workload / memory rate | New underrun observations in 10 s |
| --- | ---: |
| Native immutable 120 Hz bars, 421 MHz MIF | 0 |
| GPU desktop animation, 421 MHz MIF | 600 |
| Same GPU animation, 1352 MHz MIF | 0 |

These are polling observations, not an exact interrupt total; multiple events
could coalesce. The difference is nevertheless decisive for this workload.
Firmware queries report MIF 421 MHz, INT 200 MHz and DISP 400 MHz. An initial
query of ID 7 returned TPU 226 MHz; ID 12 is the correct DISP domain and was
queried separately. The stock DT's `mif_int_map` explicitly pairs 1352 MHz MIF
with 200 MHz INT. The `pixel-mif-test` module requests that documented MIF rate
through the Linux common clock framework and ACPM, leaving voltage/PLL sequencing
to firmware. It takes exclusive CCF rate ownership, checks all seven temperatures,
restores on reaching 55°C or after 90 seconds, and verifies the original rate.
It changes neither GPU clocks nor the INT or DISP rates.

With that one bandwidth change, the same verified fullscreen Hyprland animation
reports 119.6, 120.0 and multiple 120.2 fps windows, with zero fresh underruns.
The user confirms: **the triangle is clean and smooth, with no flashing**.
The test's automatic restore returns MIF to exactly 421 MHz. This establishes
memory bandwidth as the measured missing requirement for this 120 Hz workload;
it does not establish the minimum necessary MIF rate or a complete DVFS policy.

Evidence: `c-physical-native120.txt`, `c-registers-after-artifacts.txt`,
`c-native120-underruns.txt`, `c-gpu120-underruns.txt`, `c-bandwidth-query.txt`,

## Integrated bandwidth ownership, image D

The display driver now acquires the validated CCF memory rate before entering
120 Hz and restores the original rate after a confirmed return to 60 Hz and
idle DMA. Atomic checks discover/validate the clocks without changing rates;
mode enable performs the actual transition. It refuses an unrecognized baseline
or missing ACPM provider. ACPM activation must precede the first 120 Hz modeset.
The clock consumer is exclusive during the 120 Hz mode so another Linux client
cannot silently reduce its rate. This is a narrow handoff bandwidth floor;
a shared interconnect/devfreq governor remains future work.

The driver also clears and checks DSIM's underrun status for each transfer. A
new underrun now faults the transfer and is visible in debugfs, rather than
reporting successful data delivery solely from DECON completion. Framebuffer
references stay pinned on failure. Debugfs reports `bandwidth_active`,
`mif_rate_hz` and `dsi_underruns` alongside the existing event and DMA counters.

Image D passes native modes, GPU sharing, fullscreen animation and thermal
