## Follow-up: bootloader copies empty header fields

Host-side hashes were also checked outside the sandbox: the flashing process
sees the correct, unmodified factory file. No other fastboot/restore process
was running.

Offline inspection of the fetched ABL found its symbol table immediately before
the names at file offset `0x1bc300`; records are `<QII>` address, size, and name
offset. Linked code base is `0xffff0000f8800000`, code starts at file `0x1000`.
The saved `abl-symbols.json` and `.asm` files document the analysis (duplicate
symbol names in that JSON are collapsed; do not use it as a complete symbol list).

`fastboot_flash_boot` (`0xffff0000f8817878`) routes a version-4 image with
zero `os_version` through `fill_boot_image`. Factory `boot.img` has that zero
field. `fill_boot_image` reads the existing partition's header, then calls
`fill_boot_image_v4` (`0xffff0000f88172d4`). That helper checks byte 44 of the
incoming header; when zero, it copies up to 512 bytes of command line from the
existing header. It also fills zero OS version and ramdisk-size fields from
the previous image. This explains the exact observed retention of our old
259-byte command line after a successful flash.

`fastboot_cmd_boot` (`0xffff0000f88166ac`) also invokes `fill_boot_image` when
its completeness check requests it. A RAM boot of the unchanged factory image
was accepted (`Sending` and `Booting` OKAY), but produced no Android USB.
The user saw the bootloader, a black interval, then Google logo. This test did
not reliably exclude the stale command line: the same fill routine can copy it
into a RAM-loaded image. The user was asked to return to fastboot with
Power+Volume Down, releasing at the menu or after roughly 30 seconds if absent.

Next prepared RAM test: `out/restart-20260924/boot-stock-clean-cmdline.img`.
It is byte-identical to the verified factory image outside bytes 44..1579;
the command-line field now contains only `loglevel=4` plus zero padding.
SHA256: `07a6c1a1cee1eaaa35df8004f5246e73ef9807a1e24e3be706b602774e3b09e6`.
The explicit nonempty field avoids the command-line copy. This is a modified
factory image, not a Google-signed byte-exact image; its embedded AVB hash is
therefore stale. It is intended for temporary boot on this unlocked unit.
Sent after the user returned the phone to healthy fastboot. Both transfer and

## Screen logging direction

The OnePlus reference is
`../oneplus7pro/.work/linux-sm8150/arch/arm64/kernel/bringup_usb.c`
and its `docs/status.md` section "How we got USB". It uses a custom `brfb`
console writing the retained buffer at `0x9c000000`, with that RAM reserved
and display clocks left running. **That address and hardware setup are specific
to the OnePlus. Do not transplant them to the Pixel.**

Google's [DECON driver source](https://android.googlesource.com/kernel/google-modules/display/+/refs/heads/android-gs-pantah-5.10-android14-qpr3/samsung/exynos_drm_decon.c)
contains a framebuffer handover path (`_decon_handover_check`,
`DECON_STATE_HANDOVER`, `fb_handover.rmem`). A copy is saved alongside today's
evidence. This establishes a code path to investigate, not a proven early console.
Historical ABL logs report a 1440x3120 command-mode panel, hardware trigger,
window 5 and DPP0. Physical buffer address, stride, pixel format, reservation,
and the mechanism needed for panel refresh remain unverified on live hardware.

Follow-up binary inspection found a concrete candidate: ABL's
`display_get_framebuffer_by_index` (`0xffff0000f88055a0`) sets the index-0 draw
surface pointer to `0xffff0000fac00000`, with stride derived from width and
bits per pixel. This suggests physical `0xfac00000`, but the virtual-to-physical
mapping and live scanout still require verification. Index 1 uses `0xfc000000`
on supported boards; do not assume index 1 is present on this phone.
The surface flush callback is `display_cloudripper_flush`, which branches to
`decon_string_update` and then `decon_show_buffer_update`. A CPU write alone may
therefore not refresh this command-mode panel. The disassembly is saved in the
evidence directory. Neither candidate address has been written through by us.

The saved vendor DT blob is concatenated; today's decompiled
`saved-vendor-first.dts` is only its first entry. Historical ABL selected index 1
and applied a board DTBO, so absence of a framebuffer node in the first entry
does not establish absence from the bootloader's final DT.

Next: verify the rooted inspection boot, then verify the actual framebuffer
handoff before building a screen-only probe.
Prefer a RAM-loaded kernel with a built-in initramfs if supported. The old
observation that fastboot boot ignored an external ramdisk does not establish
that a built-in kernel initramfs requires flashing init_boot.
